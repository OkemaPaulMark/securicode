# AI Review Service

The AI Review service is responsible for contextual analysis of security findings. It consumes the evidence generated by the Scan service, checks the surrounding code, and helps developers understand whether a signal is a likely true positive, a likely false positive, or something that still needs manual review.

## Core responsibility

This service acts as a second-pass reviewer. It does not replace scanning; it validates and interprets scanner output, explains the impact, and recommends the next action.

## Tooling model

The AI agent in this service should use a controlled tool registry. The main tools we discussed are:

- Code Context Tool: read the relevant function, surrounding lines, and local code context
- Code Relationship Tool: trace callers, references, and input sources
- Security Knowledge Tool: retrieve OWASP, CWE, CVE, and secure coding guidance
- Finding Validation Tool: evaluate whether the evidence supports a true positive, false positive, or manual review outcome
- Fix Proposal Tool: prepare a reviewable remediation suggestion
- Verification Tool: rerun approved targeted checks after a fix

The scanners themselves may also be exposed as tools for targeted follow-up checks, but the full baseline assessment should still run the required scanners first.

## Responsibilities

- confirm or challenge findings using code context
- explain vulnerability findings in context
- prioritize issues by risk and impact
- map findings to OWASP and CWE references
- generate remediation guidance
- perform agentic review over affected code and findings
- retrieve trusted knowledge using a RAG layer
- enrich raw findings with recommendations, confidence notes, and classification
- support verification after an approved fix

## AI validation workflow

The platform should follow this pattern:

1. the Scan service detects a candidate issue
2. the AI service reads the affected code and related context
3. the AI service investigates the code path and supporting evidence
4. the AI service classifies the issue as a likely true positive, likely false positive, or needs manual review
5. the AI service explains the risk and recommends a fix
6. if a fix is approved, the verification step reruns the relevant checks

This means the AI is not the primary detector; it is the validator, explainer, and prioritizer.

## Design goal

This service must be trust-aware and evidence-driven. It should never invent vulnerabilities or treat untrusted repository content as a source of authority. If evidence is insufficient, it should return needs manual review instead of certainty.

## Typical endpoints

- POST /ai/enrich-findings
- POST /ai/review
- POST /ai/ask
- GET /health

## Integration points

- consumes scan findings from the Scan service
- references project context from the Project service when needed
- sends enriched results to the Reporting service
- uses controlled tools for context, validation, and remediation support

## Notes

The AI service should work as a security reasoning layer, not as the primary detector of vulnerabilities. Its job is to confirm the scanner's signal, explain it, and make it actionable for developers.
